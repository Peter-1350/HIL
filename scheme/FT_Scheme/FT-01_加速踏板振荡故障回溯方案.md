# FT-01 加速踏板振荡故障：单事件录波与回溯方案

## 1. 目的、边界与结论形式

本方案只研究一个已知故障类别：

```text
目标接口：Veh_1.Driver.AccPedal_perc
故障模式：有限时长的周期振荡
一条 Recorder 录波：仅允许包含一次该故障事件
```

这里的“回溯”不是从输出唯一重建任意输入波形，而是在已知故障类别的前提下，从不含故障接口的可观测时序估计该次振荡的参数：

```text
模式：加速踏板振荡（已知）
输出：振幅 A、频率 f、实际持续时间 D，以及置信度/可辨识性结论
```

第一阶段固定波形形状、中心值和持续时间，仅随机振幅 `A`，验证最基本的“程度可回溯性”。确认可行后，才扩展为同时随机 `A` 与 `f`。不要在第一阶段同时随机振幅、频率、持续时间、波形形状和发生工况。

本 CASE 的第一阶段也固定注入前速度为 `60`，而非每轮连续随机速度。这样可避免车速变化掩盖振幅带来的响应差异，并显著缩短单条样本的准备时间。第二阶段再采用**分层速度组**（例如 50、60、70，各组内对振幅分层抽样），而不是无约束连续随机；Blind 数据保留故障前基线车速作为上下文特征，训练/验证均按速度组分层。

## 2. 故障定义与标签

### 2.1 注入波形

建议第一版采用正弦振荡。令健康踏板参考值为 `p0`，采样周期为 `dt`，则第 `k` 个写入点为：

```text
t_k = k × dt
p_fault(k) = clip(p0 + A × sin(2π × f × t_k), 0, 100)
```

参数建议值如下；`p0`、范围和单位必须通过一次无故障基线运行确认后再固化。

| 参数 | 第一阶段 | 第二阶段 | 说明 |
| --- | --- | --- | --- |
| 波形 | 正弦 | 正弦 | 波形本身固定，避免类别变化。 |
| `p0` | 固定，例如 30% | 固定 | 应保证 `p0±A` 均在 0–100%。 |
| `A` | 分层随机，例如 2–15% | 分层随机 | 这是第一阶段的唯一待回溯连续量。 |
| `f` | 固定，例如 2 Hz | 分层随机，例如 0.5–5 Hz | 采样周期为 20 ms 时，5 Hz 每周期有 10 个点。 |
| `D` | 固定 3 s | 固定 3 s | 先不把持续时间作为待估参数。 |
| `dt` | 20 ms | 20 ms | 对应 150 个写入点；需实测 CASE 调度抖动。 |

`A` 是**命令参数**；最终标签必须由 Oracle 录波中的实际踏板序列计算。若实际注入序列为 `u(t)`，推荐记录：

```text
A_actual = (max(u) - min(u)) / 2
f_actual = 主频（FFT 或零交叉估计）
D_actual = 最后一个超过基线变化阈值的时刻 - 第一个超过阈值的时刻
```

若出现限幅，`A_actual` 可能小于命令振幅；用于回溯评价的真值应始终是 `A_actual`。

### 2.2 Oracle / Blind 的定义

同一次运行只产生一份完整 Oracle 录波，Blind 录波由它离线删除通道得到；不要并行启动两个 Recorder。

```text
Oracle：完整时间轴 + AccPedal_perc 实际写入值 + 全局响应
Blind ：与 Oracle 完全相同的时间轴和采样点，删除 AccPedal_perc 实际值及其直接镜像
```

Blind 可保留健康参考 `p0`、Key、挡位、制动、驾驶模式、车速、SOC 等上下文；其中 `p0` 是测试意图/健康参考，不是故障后的实际踏板值。若在真实应用中不存在健康参考，则应另做“无参考条件”的可辨识性试验，不能把两种问题混合。

每次运行另存一份 `case_manifest.json`。Oracle 中的故障接口和 manifest 仅用于打标签与最终评分，不能送入 Blind 回溯模型。

```json
{
  "case_id": "FT-01-A-001",
  "fault_class": "AccPedal_perc/sine_oscillation",
  "waveform": "sine",
  "p0_percent": 30.0,
  "A_command_percent": 8.0,
  "f_command_hz": 2.0,
  "D_command_s": 3.0,
  "dt_command_ms": 20,
  "seed": 20260821,
  "event_start_sim_time": "由Oracle回读/后处理填写",
  "event_end_sim_time": "由Oracle回读/后处理填写"
}
```

## 3. Recorder 边界

不需要记录从上电到停车的全部过程。为每个样本保留“相同状态下的短基线、一次故障、恢复段”即可：

```text
准备和状态对齐（不录）
→ StartRecorder
→ 正常基线 Tpre = 3 s
→ 振荡注入 D = 3 s，仅一次
→ 恢复为 p0
→ 恢复观察 Tpost = 5 s
→ StopRecorder
→ 安全收尾与下一次准备（不录）
```

因此单个训练/验证样本的推荐窗口为 11 s。若 VCU 的限扭、故障锁存或车辆动力学在 5 s 后仍未稳定，可将 `Tpost` 扩至 10 s；不要缩短故障前基线。

选择在“准备完成后”才 `StartRecorder` 的理由：

- 删除上电、起步和调速过程中的大量无关瞬态，减少数据量与特征混杂；
- 保证一条录波中仅有一个故障事件；
- 基线段仍保留故障发生前的速度、扭矩、电流、SOC 和状态机信息；
- Oracle 与 Blind 来自同一文件，完全对齐。

## 4. 状态对齐：重复试验能否使用 Loop

可以重复执行，但不能仅靠固定时间 `Loop`。每次 `StartRecorder` 前必须先满足预先定义的“可比初始状态”门控，且持续稳定一段时间。

建议的门控量如下，具体阈值先由无故障基线数据标定，不能直接假设数值或单位：

```text
Ready 灯：必须为亮（`VCU_bReadyLightSts=1`）；熄灭时重新走上电流程
Key、挡位、驾驶模式、制动状态：与目标工况一致
Vehspeed：达到注入下限 `v_inject`（本 CASE 默认 60），并连续保持 `Tstable`
前/后电机实际扭矩或 VCU 扭矩请求：位于目标带宽
SOC：位于同一窄区间；必要时还包括 BMS/MC 故障等级 = 正常
速度和扭矩在 Tstable（建议 2 s）内没有显著漂移
```

注意：踏板固定在 `p0` 时车辆可能继续加速，因而“不变速度”未必是正确条件。核心是每次**故障开始时**的速度、扭矩、档位、SOC 和状态机相近；`Tpre` 记录的实际基线会在后处理时用于做差。

推荐流程：

```text
第 i 次试验：
  1. 踏板置零、踩制动；Read Ready 灯（不录）
  2. 若 Ready 非 1：最多三次执行完整上电流程（制动释放→Key=0→空挡→制动建立→Key=1→等待3 s→Read Ready）；每次均需重新读取 Ready
  3. Ready=1 后挂挡→等待 1 s→松制动→等待 1 s→给健康踏板 `p0=30%`（均不录）
  4. 等待 `Ready=1 && Vehspeed>=60` 连续 1 s；StartRecorder，录制 Tpre；执行一次振荡；录制 Tpost；StopRecorder
  5. 踏板置零、全制动；仅当 `Vehspeed<=0` 后，才能进入下一轮并再次检查 Ready 灯
  6. 三次上电后仍 `Ready!=1`：标准 `IfThenElse` 模块的 If 判断为真后，在 Then 分支写入踏板=0、制动=100，并以 `Break` 退出最外层批次 Loop，提前结束实验。If 节点不可改业务名；若 Ready 在速度门控中熄灭，下一轮同样进入三次重试流程；若仅速度超时，则废弃本轮且不启动 Recorder
```

“连续 Tstable 均满足”比单点速度判断更重要。若当前 CASE 环境没有已验证的多条件/连续计数 Action，可用一个只返回 `Float` 的 Python 扩展 `StableFlag(...)` 计算 0/1，再以已验证的 `Read → While $stable_flag == 0 → Wait` 结构等待。这个扩展必须先按《CASE脚本编写手册》的单函数最小案例完成导入验证。

本项目的 Recorder 已确认：同一个 `RecorderFile` 可以在一个 CASE 内多次 `StartRecorder/StopRecorder`，并分别形成数据记录。因此正式实现采用一个独立 CASE 的批次 `Loop`；每轮循环仍必须先通过状态门控，再执行一次 Start/Stop。每条输出记录仍只包含一个故障事件。

CASE 的 `Loop` 仅验证过按总时间运行，不是按次数运行；应按预期试验时长配置总时长。若需要精确样本数，后处理时按实际产生的有效单事件录波计数，达到目标数后停止批次。

## 5. CASE 脚本设计

### 5.1 已确认可使用的构件

本方案只依赖《CASE脚本编写手册》中已有案例/模板验证过的 Action：

```text
Group、Write、Read、Wait、While、Loop（Time）、StartRecorder、StopRecorder
```

模型映射应从已有 case 复制，不能按名称猜写。至少需要：

```text
加速踏板输入：
[0]: env_1/第三方模型/Veh_1/InputPort/Veh_1/Driver/AccPedal_perc

车速输出：
[0]: env_1/第三方模型/Veh_1/OutputPort/Veh_1/PlantModel/PlantModel/Vehicle1/Vehspeed
```

门控如需 Key、挡位、制动、扭矩、SOC 等信号，应从已验证 case 或模型目录复制完整 Mapping、`RealTargetSource`、数据类型和单位。Recorder 内的信号不需要为了连续录波而加入 `.case/Mapping`；仅供 Read/Write 的门控信号需要加入。

### 5.2 推荐的 case 执行树

```text
批次 Loop（每轮均不录的准备）
├─ Write AccPedal_perc = 0；Write BrakePedal_perc = 100
├─ Read Ready 灯；非 1 则最多三次：制动释放→Key=0→空挡→制动建立→Key=1→等待3s→Read Ready
│  └─ 第三次仍非1：Acc=0、Brake=100、Break（退出批次 Loop）
├─ Write Gear_Button=1 → Wait 1s → Write BrakePedal_perc=0 → Wait 1s → Write AccPedal_perc=p0（不录）
├─ 等待 Ready=1 且 Vehspeed≥60 连续1s（Read + While + Wait；有 Tmax_prepare）
│  └─ Ready 中途熄灭：结束本轮等待；下一轮走重新上电流程
└─ FT-01_单次振荡录波
   ├─ StartRecorder（Oracle .dr）
   ├─ Wait 3000 ms                            # 故障前健康基线
   ├─ 3 s 振荡写入 Loop
   ├─ Write AccPedal_perc = p0
   ├─ Wait 5000 ms                            # 恢复/锁存观察
   └─ StopRecorder
└─ Write AccPedal_perc=0；Write BrakePedal_perc=100
   └─ While Vehspeed>0（Read + Wait）；车速≤0才开始下一轮
```

`StartRecorder` 必须引用已经在 EA 中创建的 Oracle `.dr` 及其真实 GUID；Start 和 Stop 的 `RecorderFile`、`RecorderID` 必须相同。不得在文档或生成器中伪造 GUID。

### 5.3 振荡写入块：CASE Loop + Python 扩展

实现文件为 `demo/pedal_oscillation.py`，提供 `SetRandomSeed`、`ResetRandomSine`、`NextSineSample` 及速度门控函数。CASE 每轮先随机振幅并复位波形，再在 3000 ms 的 `Loop` 中重复：

```text
NextSineSample → Write AccPedal_perc = $FaultPedal → Wait 20 ms
```

扩展以固定 `dt=20 ms` 推进样点序号；CASE 实际调度有抖动时，最终仍由 Oracle 中的实际踏板序列计算 `A_actual/f_actual/D_actual`。扩展模块必须先部署到测试执行器的 Python 搜索路径，并以单次调用的最小 CASE 验证导入、变量参数解析和函数状态可用，再运行批次。

下列 XML 是 Loop 内的写入模板；实际 Mapping 文本必须与顶层 `MappingItem/@Name` 逐字符一致。

```xml
<StepItem ID="test_唯一ID" Name="Write" TestType="TCS">
  <Path>/FT-01_单次振荡录波/FT-01_振荡写入块</Path>
  <Action>Write</Action>
  <Parameter xsi:type="Parameter">
    <Text>[0]: env_1/第三方模型/Veh_1/InputPort/Veh_1/Driver/AccPedal_perc = 34.702</Text>
    <Metadata xsi:type="Metadata">
      <Mapping>[0]: env_1/第三方模型/Veh_1/InputPort/Veh_1/Driver/AccPedal_perc</Mapping>
      <Constant /><IsValueInExpression>true</IsValueInExpression>
      <Value>34.702</Value><IsPythonMethod>false</IsPythonMethod>
    </Metadata>
  </Parameter>
  <Value /><Comment>k=1，计划振荡点</Comment><IsCommented>false</IsCommented>
</StepItem>
```

### 5.4 状态门控的 CASE 伪代码

以下是控制逻辑，不应在未验证表达式、比较符或 Python 扩展前直接复制成 case：

```text
prepare_deadline = now + Tmax_prepare
while not stable:
    Read Vehspeed -> Speed
    Read required torque/state/SOC -> variables
    stable = StableFlag(Speed, torque, SOC, state, target, tolerances)
    if prepare timeout: abort this run and reinitialize
    Wait 100 ms

StartRecorder
Wait Tpre
run generated 150-point injection block
Write AccPedal_perc = p0
Wait Tpost
StopRecorder
```

在 CASE 中，`Read` 仅为“是否可以开始录波”的即时控制服务；连续波形记录仍应由 Recorder 完成，不要用 Read 代替录波。

## 6. 运行前的参数抽样与文件生成

不要在 CASE 内使用当前 `demo/random_seed.py` 的无显式种子随机数直接生成正式数据集；该模块按时间设种子，不利于重放。推荐由离线生成器使用固定种子创建试验表，再按表生成 case、manifest 和波形写入块。

第一阶段建议 30 个有效样本，按振幅分层随机：

```text
2–5%：10 个
5–10%：10 个
10–15%：10 个
```

每次运行使用不同的 `case_id` 与独立 Oracle `.dr`。无故障对照应至少 10 条，且通过同样的准备、Start/Stop 和恢复流程，只是不执行振荡写入块。

目录示例：

```text
output/FT-01/
  cases/FT-01-A-001.case
  oracle/FT-01-A-001.mdf
  blind/FT-01-A-001.mdf
  manifest/FT-01-A-001.json
```

## 7. Recorder 信号集

Oracle 至少包含：

```text
实际故障接口：Veh_1.Driver.AccPedal_perc
工况：Key、Gear_Button、BrakePedal_perc、DriveMode、健康参考 p0/外部事件元数据
状态：VCU模式、MCU使能、故障等级/限扭状态（有可用接口时）
命令：VCU_TqReqCmd、VCU_Target_output_Torque、VCU_Target_output_MaxTorque
动力：前后实际扭矩、电机转速、Vehspeed
能源：BMS/MC 母线电压、电流、SOC、BMS 充放电能力
```

Blind 从 Oracle 中删除：

```text
Veh_1.Driver.AccPedal_perc 的实际写入值
其直接回读、未经过算法处理的镜像，及任何包含 A/f/D 真值的录波字段
```

若没有可记录的“健康参考踏板”模型信号，`p0` 应至少在 Blind 可用的样本元数据中作为工况参数保存；不能把 `A/f/D` 放入该元数据。

## 8. 从 Blind 数据进行回溯

本阶段可假定故障窗口边界由 case/测试编排提供，重点只评价参数回归。每条 Blind 录波按下列窗口提取特征：

```text
基线：[-3 s, 0 s)
故障：[0 s, 3 s)
恢复：[3 s, 8 s]
```

对每个响应信号计算相对基线的特征，而不是直接使用绝对值：

```text
扭矩请求/实际扭矩：峰峰值、标准差、主频、主频功率、响应时延
母线电流：峰峰值、标准差、主频及与扭矩的相干性
车速：变化率的标准差、主频、故障后净变化
状态量：限扭、使能、故障等级是否改变及其时间
上下文：基线车速、SOC、挡位、模式、p0
```

构建监督数据：

```text
X_i = Blind 特征（或多变量事件窗口）
y_i = Oracle 计算的 A_actual
```

第一版可用单调/非线性回归或随机森林回归得到：

```text
A_hat = f(X)
```

评价时使用按整条录波切分的训练/测试集，不能将同一录波的相邻滑窗同时放入训练和测试。至少报告 MAE、R²，以及轻/中/重振幅等级的混淆情况。

若 `A_actual` 增大后，Blind 特征的峰峰值或主频能量不再变化（例如 VCU 滤波、限扭或饱和），则该区间只能回溯为“严重区间”，不能声称可精确估计振幅。

## 9. 有效性、异常与停止条件

每次运行首先检查：

```text
Oracle 中确实存在一次且仅一次振荡事件；
实际 A/f/D 在规定容差内；
故障前门控量满足要求；
恢复后未出现非预期正扭矩、继电器/状态机异常或通信异常。
```

任一条件不满足时，该条记录标记 `invalid`，不得混入训练集。发生未预期保护、模型停止或无法恢复时，立即写入安全值、停止 Recorder、结束该轮并重新初始化；不要继续执行下一次振荡。

## 10. 执行顺序

1. 配置一份 Oracle `.dr`，并验证可连续记录实际踏板、扭矩、车速、电流和状态量。
2. 跑无故障基线，确定 `p0`、目标状态、门控阈值和 `Tpost`。
3. 用固定 `f=2 Hz、D=3 s`，只扫描 `A`，生成 30 条单事件 case。
4. 每次运行后由 Oracle 导出 Blind；核查每条录波只含一个故障事件。
5. 先画 `A_actual` 与扭矩/电流主频能量、峰峰值的关系，再训练回归器。
6. 仅当振幅回溯稳定后，扩展为随机 `A+f`；此时输出改为 `(A_hat, f_hat)`。
